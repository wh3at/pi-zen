# Pi tool rendering versus configured built-in execution

Research date: 2026-09-08. Installed package: `@earendil-works/pi-coding-agent` 0.85.1. Upstream `main` inspected at [`96617628e85227dedc05095717fbb1b7e878a975`](https://github.com/earendil-works/pi-mono/commit/96617628e85227dedc05095717fbb1b7e878a975).

## Finding

The narrow claim is **verified for an extension acting only through the supported `ExtensionAPI`**: Pi 0.85.1 and current upstream expose no rendering-only override/hook that can attach `renderCall`/`renderResult` to the already configured built-in definition while retaining that definition's `execute` closure. A same-name `registerTool` registration replaces the whole effective definition, including execution.

The broader claim that preservation is categorically impossible is too strong. A host that controls SDK session construction can inject a complete same-name `customTools` definition and can itself retain/configure the executor it wants. That is a different integration boundary, not a capability available to a normally loaded extension, and it still requires the host to reproduce/pass the relevant configuration. Internal `AgentSession.getToolDefinition()` also returns the full live definition, but it is not exposed by `ExtensionAPI`; mutating or reaching it through internal objects is not a supported extension mechanism.

This supports built-in-renderer fallback for an execution override, not the inverse.

## `getAllTools`, full definitions, and settings

- `getAllTools()` deliberately projects only `name`, `description`, `parameters`, `promptGuidelines`, and provenance; it omits `label`, `execute`, and renderers: upstream [`agent-session.ts` lines 947-958](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/agent-session.ts#L947-L958), installed `dist/core/agent-session.js:638-649`, and installed docs `docs/extensions.md:1677-1703` (especially `:1697`). Therefore `getAllTools` alone cannot be used to delegate to the effective executor.
- `AgentSession.getToolDefinition(name)` does return the full definition ([upstream lines 960-962](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/agent-session.ts#L960-L962); installed `dist/core/agent-session.js:650-652`). It is used by interactive mode, but the extension binding exposes only `getAllTools` ([upstream lines 2609-2612](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/agent-session.ts#L2609-L2612)). No `getToolDefinitions` API was found in either tree.
- Configured built-ins are created inside session runtime construction. In particular, read receives `autoResizeImages`, and bash receives `commandPrefix` and `shellPath`: upstream [`agent-session.ts` lines 2769-2785](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/agent-session.ts#L2769-L2785); installed `dist/core/agent-session.js:2182-2195`.
- Bash captures those options in its executor: installed `dist/core/tools/bash.js:142-157` ([official current source](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/tools/bash.ts)). Calling `createBashToolDefinition(cwd)` without options therefore loses configured `shellPath` and `commandPrefix`. Recreating read similarly loses configured image auto-resize.

## SDK distinction

The supported SDK accepts `customTools` ([`core/sdk.ts` lines 55-76](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/sdk.ts#L55-L76)) and passes them into `AgentSession` ([lines 388-402](https://github.com/earendil-works/pi-mono/blob/96617628e85227dedc05095717fbb1b7e878a975/packages/coding-agent/src/core/sdk.ts#L388-L402)). They merge with provenance `sdk` and override by name in the same registry path. This permits a controlling application to supply a fully configured executor plus custom renderers, but Pi does not inject the preconfigured built-in executor into that custom definition. `baseToolsOverride` exists at the lower-level `AgentSession` configuration, not the documented extension API, and likewise requires the caller to own the executor.

## pi-zen's current approach

`src/index.ts:160-178` identifies built-in provenance through `getAllTools`, then recreates each definition with an exported factory. `decorate` delegates execution to another newly created factory result (`src/index.ts:106-112`), not to Pi's configured definition. Consequently the provenance check is sound, but the comment/behavior does not preserve configured built-in execution. The active-set toggle (`src/index.ts:180-182`) only forces registry resolution; it cannot recover the replaced executor or its settings.

## Recommendation

Do not describe the result merely as “impossible because `getAllTools` lacks execute.” State the scoped limitation: **extension-only, supported APIs cannot replace built-in rendering while retaining the opaque configured executor**. The robust upstream solution is a supported rendering-only registration/middleware API (or a supported full-definition accessor/delegation handle whose executor remains stable across refreshes). Until then:

1. pi-zen can keep its current factory recreation only if it clearly documents that configured built-in options (currently at least bash `shellPath`/`commandPrefix` and read `autoResizeImages`) are not preserved.
2. A host-controlled SDK integration may inject wrappers with explicit equivalent settings, but this is not a drop-in extension solution and pi-zen currently intentionally skips `source: "sdk"` tools (`src/index.ts:173-178`).
3. Avoid importing private modules, casting extension context to reach `AgentSession`, or mutating the object returned by `AgentSession.getToolDefinition`; those are implementation-dependent and unsupported despite the method being public on the SDK class.

Upstream `main` retains the same relevant architecture as installed 0.85.1; it does not add a rendering-only extension API or expose `getToolDefinition` through `ExtensionAPI`.
